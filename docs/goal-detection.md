# 進球判定設計

## 框選籃框

手機架好後，使用者在 App 畫面上**拖一個框框住籃框**，只做一次（手機被碰歪再重框）。

鏡頭照常拍整個畫面，框選只是告訴 App「籃框在這裡」。App 依框的寬度自動推出**偵測區**，YOLO 只在偵測區裡找球：

```
  ┌───────────────────────────────────────────────┐
  │ 鏡頭畫面                                        │
  │            ┌───────────────────┐               │
  │  區外忽略   │ 偵測區             │  ↑ 2.5 個框寬  │
  │  （人、    │                   │               │
  │   其他球） │    ┌─────────┐    │  ← 框選框      │
  │            │    └─────────┘    │               │
  │            │      \     /      │  ↓ 1.6 個框寬  │
  │            │       籃網         │               │
  │            └───────────────────┘               │
  │             ← 左右各 0.6 個框寬 →                │
  └───────────────────────────────────────────────┘
```

好處：

- 籃框位置已知，模型只要找「球」一種東西
- 只看偵測區，裁切後球相對變大，比較準
- 場邊的人、場上其他球都在區外，直接排除
- 推論的畫面小，速度快、手機比較不燙

程式：`ml/scoreboard_ml/geometry.py` 的 `detection_roi`，App 端 `app/lib/services/goal_gate.dart` 的 `detectionRoi`（兩邊公式相同）。

## 三道檢查

程式：`ml/scoreboard_ml/goal_detector.py`。每道檢查都可單獨關閉，方便用影片比較效果。

### 1. 軌跡

- 球先出現在框的**上方**（左右可超出框 0.5 個框寬）
- 1 秒內出現在框的**下方**（滾框後掉進的球在網裡很慢，實拍最久 0.8 秒）（左右只容許超出 0.15 個框寬，深度 1.6 個框寬內）
- 上下兩點的連線，在籃框高度時要落在框內

用連線判斷，所以球太快、中間幾幀沒拍到也能判定。打框彈出（沒到下方）、由下往上（方向相反）、從框旁邊掉下（連線不在框內）都不算。

### 2. 大小比例

籃球直徑約 24 公分、籃框內徑 45 公分，真的穿過框時，**球徑 / 框寬 ≈ 0.53**。預設容許偏差 ±40%。

用來排除**麵包球**：手機只拍得到平面、分不出遠近，從框前掉下的球看起來比較大，從框後掉下的比較小，比例會超出範圍。

### 3. 籃網晃動

軌跡和大小都通過後，等 0.8 秒，期間籃網區域（框選框正下方）的畫面變化要超過門檻才確認進球。

計算時會把前後兩幀球所在的位置遮掉，所以球從網子前面掉下去不會被當成網子在晃。程式：`ml/scoreboard_ml/net_motion.py`。

### 冷卻

確認進球後 2 秒內不再判定，避免同一球算兩次。

## 參數

`GoalConfig` 的預設值，之後依實拍影片調整：

| 參數 | 預設 | 說明 |
| --- | --- | --- |
| `max_transit_s` | 1.0 | 從框上方到框下方的最長時間（秒） |
| `above_margin` | 0.5 | 上方區左右可超出框的寬度（框寬倍數） |
| `crossing_tol` | 0.1 | 穿越點可超出框左右的容許量 |
| `below_margin` | 0.15 | 下方區左右可超出框的寬度 |
| `below_depth` | 1.6 | 下方區深度 |
| `expected_ratio` | 0.53 | 球徑 / 框寬 |
| `size_tol` | 0.4 | 比例容許偏差 |
| `net_window_s` | 0.8 | 等待籃網晃動的時間（秒） |
| `net_threshold` | 0.04 | 籃網變化量門檻（0～1） |
| `cooldown_s` | 2.0 | 冷卻時間（秒） |

## 出手判定（罰球模式，設計中）

罰球模式要算投幾進幾，但上面的判定只回報進球，沒進的球不會留下事件。還沒實作，打算這樣做：

1. 球進到框上方區，開一次出手
2. 確認進球就記「進」；逾時球還沒穿過框就記「沒進」
3. 出手結束後冷卻，避免籃板補進或球彈起來多算一次

### 用什麼影片驗證

先用 10-30 的 3v3 影片。判定只看籃框周圍，球從哪裡投來不影響邏輯，而且鬥牛有人擋、有上籃和搶籃板，比罰球難。

| 能驗的 | 驗不到的 |
| --- | --- |
| 到籃框附近的出手抓到幾成（標記 66 顆：21 進、45 沒進） | 碰不到偵測區的大麵包球會不會漏算（標記沒列這種球） |
| 進或沒進有沒有判對 | 出手總數：標記沒列的出手，判定出來時要回去看畫面才知道是真的出手還是誤判 |
| 籃板、補進會不會多算 | 連續罰球的節奏和冷卻衝不衝突 |

驗不到的部分，最後錄一段罰球確認。

## 已知限制

- **擺放角度影響很大**：手機正對籃框、高度和籃框差不多時，框在畫面上幾乎是一條線，前後的球都疊在上面。腳架架高往下拍，或斜 45 度拍，誤判會少很多。
- **框選框的大小會影響比例檢查**：框得太大或太小，球框比例會偏，`expected_ratio` 可能要依實際框法調整。
- **籃網晃動門檻受光線影響**：逆光、閃爍的燈光可能讓網子區域本來就有變化，需要實拍調整門檻。
- **廣角拍法**：籃框在畫面裡變小，球可能只有 30px 左右，需要高解析度；手機即時分析的解析度通常比錄影低，要實測。

## 驗證方式

1. 單元測試：`ml/tests/`，用合成軌跡測各種情況（進球、打框彈出、由下往上、麵包球、冷卻等）
2. 影片評估：`ml/scripts/eval_video.py`，和人工標記比對準確率、召回率，並輸出標註影片檢查誤判

## 手機規格的模擬（2026-11-02）

用 10-30 半場 5 支影片（標記進球 21 球，幾乎都是 Claude 從截圖判斷，還沒人工驗證）重播手機規格。參數是在同一批影片上挑的，實戰可能更差。

| 籃框寬度（佔畫面） | 模型輸入 | 幀率 | 籃網門檻 | 判對 | 誤判 |
| --- | --- | --- | --- | --- | --- |
| 2.7%（1080p，這批影片的機位） | 320 | 30 | 0.03 | 6 | 9 |
| 2.7%（1080p） | 640 | 30 | 0.03 | 8 | 8 |
| 5.4%（相當於手機架近一倍） | 320 | 30 | 0.03 | 7 | 12 |
| 5.4% | 640 | 30 | 0.03 | 15 | 11 |
| 5.4% | 640 | 15 | 0.04 | 12 | 6 |

結論：籃框要佔畫面寬度 1/20 以上，模型輸入要 640，兩個都要才有效。App 目前用 640 輸入、門檻 0.04。

S23 實測（1920×1080、640 輸入）：CPU 每張 267 ms，約 4 fps；GPU 每張推論 30 ms、前處理 11 ms，約 16 fps。實測時鏡頭對著暗處，還沒用真的球驗證座標對齊，也還沒驗證手機反過來拿的情況。
